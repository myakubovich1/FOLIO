# Database cutover and verification

`DATABASE_URL` is the canonical Tiger Cloud/PostgreSQL destination. A configured failure stops the application; there is no implicit SQLite fallback. Preserve `.env.local` and the old database before switching services. Connection URIs belong only in the ignored file or deployment secret editor.

1. Stop the source application during final cutover. Do not run two writable copies.
2. Set the target `DATABASE_URL` including verified TLS. If its private CA is required, add `sslmode=verify-full&sslrootcert=/absolute/path/to/trusted-ca.pem`. Obtain that CA from the provider's authenticated console or a trusted provider distribution; do not disable certificate verification or trust an unverified network certificate.
3. Run `npm run db:migrate`.
4. For the established local PostgreSQL source, put its URI in `FOLIO_SOURCE_DATABASE_URL` locally and run `npm run db:transfer`. For SQLite, leave that source URL unset and optionally set `FOLIO_SOURCE_SQLITE_PATH` (default `.data/folio.sqlite`). A source SQLite file must already have the normalized Folio schema; the original adapter performs the legacy upgrade before this operation.
5. The transfer takes a consistent read-only source snapshot and copies owner-scoped records, sources, all assessment revisions, immutable passport snapshots, session hashes, sharing/revocation state, audit history and deletion guards. It excludes unconfirmed upload previews. No source writes occur. A destination transaction commits the entire copy or rolls it back. Existing destination owners or deletion guards are never overwritten. A source deletion conflicting with an active destination owner requires reconciliation.
6. Run `npm run providers:check`, `npm run db:seed`, and the database tests with `FOLIO_TEST_DATABASE_URL` set privately to the test target. Start Folio, inspect history, make a correction, issue/share/revoke a passport, stop/restart, and inspect the same session. Compare the owner-filtered continuous aggregate with deterministic assessment totals.

This is a one-time copy with idempotent owner skipping, not replication or a merge engine. A rerun preserves destination changes; it does not reapply later source changes. Do not resume writes against the source after cutover. Keep the retained source for recovery under the same access restrictions as financial data. `output/verification/database-transfer.json` contains sanitized row counts and timestamps, never credentials or owner identifiers.

Timescale uses a date-partitioned transaction hypertable and a daily continuous aggregate grouped by owner and currency. The dashboard queries monthly sums from that aggregate; corrections explicitly refresh covered dates, including historical materialized buckets. A shared PostgreSQL advisory lock serializes refresh procedures across app instances, avoiding Timescale's concurrent-refresh refusal. Owner deletion removes raw rows, refreshes aggregates, and retains a financial-data-free guard until cleanup succeeds. The application checks both owner and deletion guard on history reads.

`tests/transfer.test.ts` exercises a real SQLite → PostgreSQL copy, two currencies/owners, two assessment revisions, immutable earlier passport, live and revoked shares, session persistence, reopen/restart, exact monthly totals, rerun preservation and rollback. `tests/tiger.test.ts` exercises concurrent database connections, correction refresh and interrupted deletion cleanup. Local Timescale execution is distinct from Tiger Cloud verification in the sponsor report.
