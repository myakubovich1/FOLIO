# Evaluation scope

`npm test` verifies exact financial calculations and factor contributions, fixed model reproducibility, monotonic liquid balance changes, identity/unit-scaling invariance, refunds, transfers, borrowing, direction conflicts, missing history, seasonal coverage, decimal parsing, duplicates and overlapping/gapped statements. It also tests owner isolation, source previews, exports, immutable disclosure, expiry/revocation/deletion and actual Timescale when its test URI is present. These software tests do not establish real-world repayment accuracy or general fairness.

`evals/cases.json` contains human-authored expected profile scores/totals and ambiguous classification expectations. Expected newcomer income = 12 × $4,200 + a $100 initially misclassified returned deposit; expense = 12 × $3,000. Freelancer alternates $7,000/$3,000 receipts, farmer has four KES540,000 harvest receipts in two years, merchant has KES140,000 monthly receipts; each has the documented $/KES100 review deposit. Limited evidence contains only six dated rows and must abstain. Review/correction removes that deposit from income when confirmed as an own transfer.

`npm run eval:ai` separately records deterministic numerical consistency and evidence-ID validation for each profile, then (only with configured credentials) live Gemini explanation and classification results. Income classification of an ambiguous generic deposit or prompt-injection description must abstain; explicit evidence can still safely abstain. Report correctness and abstention separately. `tests/extraction.test.ts` supplies human-authored structured extraction fields and checks exact decimals, original PDF-page mapping, missing amounts and malformed dates. These are validation tests, not measured live extraction accuracy. The actual synthetic two-row PDF check matched both rows by date, amount and category, with valid page references and reconciliation; this is a small fixture, not general document accuracy.

Explanation architecture deliberately allows only schema claim kinds and permitted evidence references, not model-written financial prose. Strict unknown-field validation rejects unsolicited numerical claims; all displayed figures/factor contributions are rendered from named current deterministic metrics. Tests reject nonexistent/wrong-kind citations and verify source prompt-injection cannot change results or expose optional snapshot data. References are scoped to the current owner and revision, not a model-provided owner ID. A schema-valid extraction/classification may still be incorrect; reconciliation and human review remain essential.

Model/prompt versions are recorded on explanations; prompt version folio-evidence-v3; configured model gemini-3.1-flash-lite. Actual profile explanation checks pass5/5 and three missing-data/unsupported-approval/improvement questions pass3/3. One four-case classification run passes4/4 (two explicit categories, ambiguous deposit abstention, instruction-text abstention). Full-batch failures and earlier 3.8 Flash quota exhaustion are recorded, not erased; inspect current output/verification reports. These small synthetic checks do not measure real-world accuracy. Provider retries are bounded and failures are recoverable. No raw personal financial prompt logging is enabled.

Query performance: `npm run db:benchmark` measures ten sequential refresh-plus-monthly queries per actual fixed dataset on local PostgreSQL17/Timescale2.30.2. Dataset sizes are 61 newcomer, 61 freelancer, 101 farmer, 61 merchant and six limited records after adding explicit synthetic asset reallocations that reconcile statement balances. Current measured medians:27.04,36.13,31.59,35.06,20.72ms; maxima490.18,506.26,269.42,328.69,38.73ms. Browser/review tools were active during this measurement. These include refresh overhead on this local machine with existing demo data, not networked cloud performance, concurrency capacity or a claimed multiplier. Reproducible raw measurement output is output/verification/query-measurements.json.

Browser evidence includes saved demo and isolated trusted-identity private owner journeys on desktop/mobile. The latter verifies application authorization and UI, not Auth0's external login. Screenshots are heuristic visual evidence, with automated overflow and axe checks; they are not a user study or complete accessibility certification. Container/public-host rollout and real Auth0 login remain separate. Actual public synthetic live-provider UI requests are captured in output/verification/live-browser.json.

Execution findings materially changed the pipeline: an instruction-like loan description was held for manual review before keyword reduction; benign system-payment descriptions remain eligible. Classification target/evidence IDs now use the authorized per-request enum in the provider schema as well as runtime validation. Unsupported IDs cannot be accepted. Missing/partial financial costs are explicitly unknown rather than confirmed zero expenses or disposable income across UI, explanations and PDF.
