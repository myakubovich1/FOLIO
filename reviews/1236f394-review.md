## P2 — Financial UX: positive-amount expense silently excluded

**File:** `server/assessment.ts:17`, `src/main.tsx:23`

**Reproduction:** Load newcomer. In the Records table, change `newcomer-correction` (amount +10 000, i.e. +$100) from `income` to `expense`. The assessment shows income drops by 10 000 but expenses are **unchanged**. The chart similarly contributes 0 to that month's expense bar (`Math.max(0,-10000)=0`).

**Root cause:** `if(r.category==='expense'&&r.amount<0) expenses-=r.amount` intentionally counts only negative expense amounts, consistent with the contract ("absolute sum of negative expense records"). A positive-amount record reclassified to `expense` is excluded from both income and expenses—net cash flow increases even though the user believes they are acknowledging a cost.

**Impact:** Counterintuitive silent result. A borrower who has a positive-amount refund or adjustment and mis-categorizes it as `expense` (intending to mark it as a cost) will see a misleading improvement in assessed capacity. No current UI warning explains the sign convention.

**Suggested fix:** In the Records table, when a positive-amount record has its category set to `expense`, show an inline caution: "Positive amounts are not counted as expenses in this model; use 'refund' if this offsets a prior expense." Alternatively display `(not counted as expense — positive amount)` beside the dropdown.

## P2 — Chart scale: per-record max vs. per-month sum

**File:** `src/main.tsx:23`

**Reproduction:** Any profile where a month has more than one income record. For newcomer, February has two income records: `newcomer-1-income` (420 000) and `newcomer-correction` (10 000), monthly sum = 430 000.

```js
// scale component for income:
Math.max(...b!.records.filter(r=>r.category==='income').map(r=>r.amount), ...)
// → 420 000  (max individual record)

// February bar height:
Math.min(100, 430000/420000*100) → Math.min(100, 102.4) → 100%
// January bar height: Math.min(100, 420000/420000*100) → 100%
```

Both months render at identical height even though February has more income. Any month with split income records will silently clip.

**Impact:** The chart is incorrect for any borrower with multiple income records per month. After a profile acquires AI-classified or real records, this would become frequent. The misleading flatness could hide income spikes or tell a different story than the assessment figures.

**Suggested fix:** Replace the income scale component with a per-month maximum:
```js
const monthKeys = Array.from(new Set(b!.records.map(r=>r.date.slice(0,7))));
const maxMonthlyIncome = Math.max(
  ...monthKeys.map(m => b!.records.filter(r=>r.date.startsWith(m)&&r.category==='income').reduce((n,r)=>n+Math.max(0,r.amount),0)),
  1
);
const maxMonthlyExpense = Math.max(
  ...monthKeys.map(m => b!.records.filter(r=>r.date.startsWith(m)&&r.category==='expense').reduce((n,r)=>n+Math.max(0,-r.amount),0)),
  1
);
const scale = Math.max(maxMonthlyIncome, maxMonthlyExpense);
```

## P3 — "Choose another profile" leaves session cookie active; page refresh resumes old session

**File:** `src/main.tsx:18`

```js
onClick={() => { setState(null); setEvidence(null); setShareUrl(''); }}
```

No API call is made. The `folio_session` cookie remains valid (7-day `maxAge`). If the user clicks "Choose another profile" and then refreshes the page *before* clicking "Build your demo profile", `GET /api/state` succeeds and the old session data is restored, showing the previously loaded borrower rather than the landing page. This contradicts the user's intent.

**Impact:** Low severity in the synthetic demo context, but could confuse reviewers expecting a clean reset. Also orphans session rows in the database since they are never deleted.

**Suggested fix:** Either (a) call `POST /api/session` immediately (overwriting the cookie) to start fresh with a blank state, or (b) explain in the UI that "Refresh will resume your previous profile until you start a new demo."
